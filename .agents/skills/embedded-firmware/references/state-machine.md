# 状态机设计

## 建模

- 只有在状态、事件和转换关系能降低复杂度时才引入状态机。
- 定义状态、事件、守卫条件、动作、初始状态和终止或安全状态。
- 状态由状态机所有；外部模块发送命令或事件，不直接写内部状态。
- 区分请求事件与已发生事实，避免命名混淆。

## 转换

- 为每个允许转换定义源状态、事件、守卫、动作和目标状态。
- 明确非法事件、未知状态、重复事件和转换动作失败时的行为。
- 未知状态不得简单 `default: break`；根据安全需求上报、恢复到安全状态或触发受控故障。
- 仅在需要时提供 Entry、Execute、Exit 动作，不为简单状态强制生成空函数。

## 实现选择

- 小型状态机可以使用 `switch`；规则密集时可使用转换表；层次复杂时可拆分子状态机或使用层次模型。
- 不规定固定状态数量。以职责、转换数量、共享数据和可测试性判断是否拆分。
- 将长业务操作放到独立函数或服务中，但保持转换动作的原子性和失败语义清晰。

## 事件与时间

- 定义事件队列容量、优先级、合并、丢弃和满载策略。
- 超时使用非阻塞计时或定时事件，并正确处理计数器回绕、取消和迟到事件。
- 多生产者或 ISR 投递事件时检查并发安全和 API 上下文限制。

## 验证

- 使用转换表或图说明复杂状态流。
- 测试正常转换、非法事件、边界时序、动作失败、队列满、复位和安全状态。
- 对安全关键状态机检查不可达状态、死锁状态和无界重试。
