# 架构与模块边界

## 核心原则

- 新建工程或用户要求架构重构时，必须先建立显式分层目录；修改已有工程时先识别并保持其分层，除非任务包含迁移。
- 让依赖指向稳定抽象，限制硬件、RTOS 和厂商 SDK 细节的扩散。
- 让模块拥有自己的状态，并通过明确接口、消息或事件协作。
- 允许有证据的跨层调用；记录原因，不为消除一次调用额外制造空壳层。

## 强制目录分层

新建嵌入式工程或执行整体架构重构时，必须在源码根目录建立以下可直接辨认的层级：

```text
Project/
├── App/             # 应用层：产品流程、模式、状态机和用户交互
├── Middleware/      # 中间件层：协议、算法、存储、网络和可复用服务
├── BSP/             # 板级支持层：板载设备、引脚、总线实例和资源组合
├── Drivers/         # 驱动层：通用器件驱动和外设驱动
├── Platform/        # 平台层：MCU、HAL、RTOS、启动与系统适配
├── Config/          # 配置层：板型、功能开关和构建配置
└── ThirdParty/      # 第三方代码：厂商库和外部组件
```

至少必须明确分出 `App/`、`BSP/` 和 `Drivers/`；需要算法、协议、RTOS 或多平台支持时，再使用其余层。目录可以增加数字前缀，但不得使用含义不清的 `Common/`、`Misc/` 或 `Other/` 代替核心层。

推荐依赖方向：

```text
App → Middleware / BSP
Middleware → BSP / Platform
BSP → Drivers / Platform
Drivers → Platform
Platform → 厂商 SDK / RTOS / Startup
```

- 禁止下层反向依赖 App。
- 使用第三方组件时，通过所属层的适配接口暴露给上层，不让 App 到处直接包含第三方头文件。
- 将自研文件放入其职责对应目录，不与 CMSIS、HAL、SPL 或自动生成文件混放。
- 在 IDE 工程分组、构建脚本和磁盘目录中保持相同层级名称，避免只在 IDE 中“看起来分层”。
- 已有工程使用 `User/Hardware/System/Library` 等结构时，先建立与上述层级的映射；普通功能修改不得擅自搬迁全工程。

## 设计检查

- 明确模块职责、公开接口、内部状态和允许的依赖方向。
- 区分机制与策略：底层提供能力，上层决定产品策略。
- 将平台相关代码集中到可替换边界，但不要为一个简单调用过度抽象。
- 对测试替身、多个硬件变体或明确移植需求，优先使用接口或适配层。
- 变更公开接口时检查所有调用者、配置、链接脚本和文档。

## 例外记录

当性能、启动顺序、ISR 延迟、代码尺寸或既有 ABI 要求偏离默认分层时，说明约束、替代方案、选择理由和影响范围。
